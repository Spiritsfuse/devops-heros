# 02 - Metrics, Logs & Traces

These are the three common observability signals.

```text
Metrics
Logs
Traces
```

---

# 1. Metrics

Metrics are numbers measured over time.

Examples:

```text
CPU usage
Memory usage
Request count
Error count
Request latency
```

Example:

```text
http_requests_total = 1200
```

Another:

```text
http_request_duration_seconds = 0.25
```

Think:

> Metrics answer "HOW MUCH?" or "HOW OFTEN?"

---

# 2. Logs

Logs are messages/events produced by applications and systems.

Example:

```text
2026-09-28 18:20:01 INFO User logged in
2026-09-28 18:20:03 INFO Payment started
2026-09-28 18:20:05 ERROR Database timeout
```

Think:

> Logs tell us what happened.

---

# 3. Traces

A trace follows one request across multiple services.

Example:

```text
Trace ID: abc123

Browser
 |
 +-- API Gateway       20ms
 |
 +-- Order Service     80ms
 |
 +-- Payment Service   120ms
 |
 +-- Database          600ms
```

Total:

```text
820ms
```

We can see where time was spent.

# Kubernetes Demo

Start a cluster:

```bash
kind create cluster --name session20
```

#### 💡 Command Breakdown (`cmd-explained`):
- `kind`: Stands for **K**ubernetes **in** **D**ocker. A tool for running local Kubernetes clusters where each node is a Docker container.
- `create cluster`: Tells `kind` to pull a node image, start a container running systemd/containerd, deploy the Kubernetes control plane components (`kube-apiserver`, `etcd`, `kube-controller-manager`, `kube-scheduler`), and generate a local `kubeconfig`.
- `--name session20`: Assigns a distinct name to the cluster (prefixing container names as `session20-control-plane` and setting the context as `kind-session20`).
- **Theory Connection**: Sets up the local playground infrastructure to observe application metrics, logs, and events without needing cloud VMs.

Apply the demo:

```bash
kubectl apply -f k8s-demo/
```

#### 💡 Command Breakdown (`cmd-explained`):
- `kubectl`: The Kubernetes command-line interface.
- `apply`: The core **declarative** configuration command. It reads your YAML manifests, calculates the 3-way diff between the previous config, the live state, and the new YAML, and makes the necessary cluster updates.
- `-f` (or `--filename`): Specifies the file path or directory. Passing a directory path (`k8s-demo/`) recursively reads and applies all YAML files found inside it.
- **Theory Connection**: Deploys the application workload that will generate the metrics and log streams we want to observe.

Check pods:

```bash
kubectl get pods
```

#### 💡 Command Breakdown (`cmd-explained`):
- `get`: API query command to fetch and list Kubernetes resources.
- `pods`: The resource type. A Pod is the smallest deployable computing unit in Kubernetes, wrapping one or more containers.
- **Output Columns Explained**:
  - `READY 1/1`: 1 container is ready out of 1 configured in the pod.
  - `STATUS Running`: The container runtime has started the container successfully.
  - `RESTARTS 0`: Number of times the container crashed and was restarted by the kubelet.
  - `AGE 10s`: Time elapsed since the pod resource was created.

Expected shape:

```text
NAME                      READY   STATUS    RESTARTS   AGE
session20-demo-xxxxx      1/1     Running   0          10s
```

The exact Pod name is generated by Kubernetes.

# Logs

```bash
kubectl logs deployment/session20-demo
```

#### 💡 Command Breakdown (`cmd-explained`):
- `logs`: Queries the `kube-apiserver`, which asks the worker node's `kubelet` to read the log files generated on disk by the container engine.
- `deployment/session20-demo`: Instead of looking up the random pod hash name (`session20-demo-xxxxx`), referencing the deployment directly lets `kubectl` select and stream logs from the first matching active pod in that deployment.
- **Theory Connection**: Retrieves the **Logs signal (Events)**. This tells you *what* the application did (e.g., initialized routes, processed an incoming request).

Expected:

```text
Session 20 observability demo started
Request received
Health check OK
```

---

# Describe the Workload

```bash
kubectl describe deployment session20-demo
```

#### 💡 Command Breakdown (`cmd-explained`):
- `describe`: Emits a detailed multi-section audit of the specified Kubernetes resource.
- `deployment session20-demo`: Identifies the deployment controller managing replica sets and rolling updates.
- **What it provides for Observability**:
  - `Replicas`: Expected vs actual active pods (Metric-level overview).
  - `Conditions`: High-level health markers (`Available`, `Progressing`).
  - `Events`: Chronological audit log recorded by controllers (e.g., `ScalingReplicaSet`, `SuccessfulCreate`, image pull progress). This connects logs with system events.

This gives details about:

```text
Labels
Replicas
Images
Events
Pods
```

# Clean Up

```bash
kubectl delete -f k8s-demo/
```

#### 💡 Command Breakdown (`cmd-explained`):
- `delete`: Sends DELETE requests to the Kubernetes API to terminate and tear down resources.
- `-f k8s-demo/`: Targets every resource defined in the manifests within the `k8s-demo/` directory, gracefully terminating pods and services.

Optionally remove the whole cluster:

```bash
kind delete cluster --name session20
```

#### 💡 Command Breakdown (`cmd-explained`):
- `kind delete cluster`: Stops and removes the Docker container hosting the control plane (`session20-control-plane`) and removes the `kind-session20` context from your `~/.kube/config`.
- `--name session20`: Specifies the exact cluster to delete, protecting any other kind clusters you may have running.

# Important

A log tells you:

```text
WHAT happened
```

A metric tells you:

```text
HOW MUCH / HOW OFTEN
```

A trace tells you:

```text
WHERE the request spent time
```

---

### 📚 Tech Jargons Demystified:
- **Cardinality**: The number of unique values a metric label can have. High cardinality (like user email or transaction ID in Prometheus) increases memory usage drastically.
- **Structured Logging**: Formatting log entries as JSON or key-value pairs (e.g., `{"level":"info","event":"user_login","user_id":42}`) so search engines (like Loki or Elasticsearch) can index and filter them instantaneously.
- **Span**: The basic building block of a **Trace**. Represents a single unit of contiguous work (e.g., an HTTP GET or a database SELECT) with a start time, duration, and status.
- **Trace ID**: A globally unique identifier propagated across network headers (like W3C `traceparent`) so all independent services handling the same user request can be tied together.
