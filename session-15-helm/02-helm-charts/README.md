# Helm Charts

```text
helm install my-app ./my-chart
```

One command. Entire application deployed.

---

## 1. What is a Helm Chart?

A Helm Chart is a directory with a specific structure. It holds:

* Kubernetes YAML templates
* Default values
* Chart metadata

```text
my-chart/
  Chart.yaml
  values.yaml
  templates/
    deployment.yaml
    service.yaml
```

---

## 2. Create Your First Chart

Run:

```bash
helm create demo-chart
```

#### 💡 Command Breakdown (cmd-explained):
* `helm create demo-chart`: Scaffolds a complete starter Helm chart named `demo-chart`. Creates `Chart.yaml`, `values.yaml`, `.helmignore`, and a `templates/` folder pre-populated with standard production templates.

Expected output:

```text
Creating demo-chart
```

Check what was created:

```bash
ls demo-chart/
```

#### 💡 Command Breakdown (cmd-explained):
* `ls demo-chart/`: Lists top-level chart components: `Chart.yaml` (metadata), `charts/` (subcharts/dependencies), `templates/` (manifest templates), and `values.yaml` (default variables).

Expected output:

```text
Chart.yaml  charts  templates  values.yaml
```

---

## 3. Look Inside the Chart

```bash
ls demo-chart/templates/
```

#### 💡 Command Breakdown (cmd-explained):
* `ls demo-chart/templates/`: Displays the templated Kubernetes resources generated by the scaffolding: `deployment.yaml`, `service.yaml`, `ingress.yaml`, `hpa.yaml`, `serviceaccount.yaml`, along with `NOTES.txt` (post-install user guide) and `_helpers.tpl` (reusable template partials).

Expected output:

```text
NOTES.txt  _helpers.tpl  deployment.yaml  hpa.yaml  ingress.yaml  service.yaml  serviceaccount.yaml
```

This is a full working chart generated by Helm.

## 4. Render Without Deploying

Check what Kubernetes YAML will be generated:

```bash
helm template my-release demo-chart
```

#### 💡 Command Breakdown (cmd-explained):
* `helm template <release-name> <chart-path>`: Client-side dry run. Combines `values.yaml` with the Go templates inside `templates/` and outputs the resulting raw YAML manifests to stdout without contacting the cluster. Essential for syntax validation before deployment.

Expected output (partial):

```text
---
# Source: demo-chart/templates/serviceaccount.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-release-demo-chart
---
# Source: demo-chart/templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
...
```

This is very useful for debugging.

## 5. Install the Chart

```bash
helm install demo-release demo-chart
```

#### 💡 Command Breakdown (cmd-explained):
* `helm install demo-release demo-chart`: Renders the chart locally and submits the resulting resources to the cluster API server under release name `demo-release`.

Expected output:

```text
NAME: demo-release
LAST DEPLOYED: ...
NAMESPACE: default
STATUS: deployed
REVISION: 1
```

Check the pods:

```bash
kubectl get pods
```

---

## 6. List Releases

```bash
helm list
```

#### 💡 Command Breakdown (cmd-explained):
* `helm list`: Displays all deployed Helm releases in the current namespace, verifying release status is `deployed` at revision 1.

Expected output:

```text
NAME            NAMESPACE   REVISION   STATUS     CHART
demo-release    default     1          deployed   demo-chart-0.1.0
```

---

## 7. Uninstall

```bash
helm uninstall demo-release
```

#### 💡 Command Breakdown (cmd-explained):
* `helm uninstall demo-release`: Reverses the release, cleanly terminating all pods, services, and associated resources.

Expected output:

```text
release "demo-release" uninstalled
```

## Key Learning

```text
helm create    = generates a working chart skeleton
helm template  = renders YAML locally (dry-run)
helm install   = deploys the chart to Kubernetes
helm uninstall = removes all resources created by the release
```

### 📚 Tech Jargons Demystified:
* **Chart Skeleton:** The standardized initial folder layout generated by `helm create`, adhering to official Kubernetes and CNCF packaging conventions.
* **NOTES.txt:** A templated plain text file inside `templates/` that evaluates at install/upgrade time to display helpful instructions (e.g. how to retrieve service URLs or passwords) directly on the user's terminal.
* **_helpers.tpl:** A template partial file (prefixed with an underscore `_` so Helm does not treat it as a standalone Kubernetes manifest) defining shared template snippets (`{{- define "demo-chart.fullname" -}}`).
* **Client-Side vs Server-Side Dry Run:**
  * `helm template`: Pure client-side parsing; does not validate whether Kubernetes APIs or CustomResourceDefinitions actually exist in the cluster.
  * `helm install --dry-run=server`: Submits manifests to `kube-apiserver` in dry-run mode, executing real server-side schema and admission webhook validations without persisting resources to etcd.
